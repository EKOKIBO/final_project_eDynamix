# ZIPShip — Система за проследяване на пратки

Конзолно приложение на Python за регистриране, търсене, редактиране и обработка на
пратки. Данните се пазят в една SQLite таблица, а многопоточността се използва за
симулиране на едновременна обработка на няколко пратки.

---

## 1. Екип и разпределение на работата

| Участник    | Разработена част                                                                                                                  |
|-------------|-----------------------------------------------------------------------------------------------------------------------------------|
| **Емануил** | `shipments.py` + `workers.py` — домейн модел `Shipment`, валидации, формати, история на статусите, бели списъци за сортиране/търсене/филтриране, многопоточна обработка и логване   |
| **Даяна**   | `database.py` — SQLite слой, CREATE/INSERT/SELECT/UPDATE/DELETE, параметризирани заявки, търсене и филтриране, статистика         |
| **Жасмина** | `main.py`  — конзолно меню, обработка на грешки, цветен интерфейс                             |


---

## 2. Кратко описание

ZIPShip позволява:

* добавяне на пратка с автоматично генериран уникален номер (`ZIP1001`, `ZIP1002`, …);
* преглед на всички пратки, със сортиране по тегло, дата, град, номер или статус;
* търсене по номер за проследяване;
* търсене по дума в подател, получател, начален или краен град (независимо от
  малки/главни букви, включително на кирилица);
* филтриране по статус, град и/или минимално тегло;
* промяна на статус с автоматичен запис в историята;
* преглед на пълната история на статусите;
* редактиране на подател, получател, градове и тегло;
* изтриване с потвърждение;
* едновременна обработка на недоставени пратки в няколко нишки;
* обща статистика (COUNT / SUM / AVG + разбивка по статус) директно от SQL.

## 4. SQLite база данни

Използва се **една** таблица без връзки, външни ключове, JOIN или тригери.

```sql
CREATE TABLE IF NOT EXISTS shipments (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    tracking_number  TEXT UNIQUE NOT NULL,
    sender_name      TEXT NOT NULL,
    recipient_name   TEXT NOT NULL,
    origin_city      TEXT NOT NULL,
    destination_city TEXT NOT NULL,
    weight           REAL NOT NULL,
    current_status   TEXT NOT NULL,
    status_history   TEXT NOT NULL,
    created_at       TEXT NOT NULL
);
```

| Колона | Тип | Описание |
|---|---|---|
| `id` | INTEGER | Първичен ключ, автоматично увеличаване |
| `tracking_number` | TEXT | Уникален номер за проследяване (3–20 символа: `A–Z`, `0–9`, `-`, `_`) |
| `sender_name` | TEXT | Име на подател (2–60 символа, задължително съдържа буква) |
| `recipient_name` | TEXT | Име на получател |
| `origin_city` | TEXT | Начален град |
| `destination_city` | TEXT | Краен град |
| `weight` | REAL | Тегло в килограми, 0.001 – 1000 |
| `current_status` | TEXT | Един от осемте позволени статуса |
| `status_history` | TEXT | Многоредов текст, по един ред на промяна |
| `created_at` | TEXT | Дата и час на създаване, формат `YYYY-MM-DD HH:MM:SS` |

### Статуси

`Регистрирана` → `Приета в офис` → `В процес на обработка` → `Транспортира се` →
`Пристигнала в център` → `Предадена на куриер` → `Доставена` / `Неуспешна доставка`

Последните два са **крайни**: пратка в краен статус не се обработва от нишките, а
ръчното ѝ връщане в обработка изисква изрично потвърждение от менюто.

### История на статусите

Историята се пази като обикновен текст в колоната `status_history`. При всяка промяна
новият ред се добавя към съществуващия:

```
2026-05-04 10:12:33 - Регистрирана
2026-05-04 11:40:07 - В процес на обработка
2026-05-04 15:02:58 - Транспортира се
```

### Безопасност на заявките

Всички потребителски стойности се подават през `?` плейсхолдъри:

```python
cursor.execute("SELECT * FROM shipments WHERE tracking_number = ?", (tracking_number,))
```

`ORDER BY` и имената на колони не могат да се параметризират, затова се строят
единствено от бели списъци в `shipments.py` (`SORT_FIELDS`, `SEARCH_FIELDS`,
`EDITABLE_COLUMNS`). Непознат ключ води до `ValidationError`, а не до вмъкване на
текст в заявката.

`LIKE` шаблоните се екранират (`%`, `_`, `\`) и се изпълняват с `ESCAPE '\'`.
Тъй като вграденото `LOWER()` на SQLite не работи с кирилица, в базата се регистрира
собствена функция `PYLOWER`, която ползва `str.lower()` на Python.

## 5. Многопоточна част

Реализирани са и **двата** позволени варианта; изборът между тях се прави от меню 7.

**Вариант 1 — `ThreadPoolExecutor`** (`workers.process_batch`)
Пуска до `MAX_WORKERS = 3` нишки и разпределя пратките чрез `executor.map()`, който
запазва реда на резултатите.

**Вариант 2 — клас, наследяващ `Thread`** (`workers.ShipmentWorker`)
Създава по една нишка на пратка и работи с `start()` / `run()` / `join()`.

### start() / run() / join()

* `start()` — създава нова нишка на ниво операционна система и в нея извиква `run()`.
  Главната нишка продължава веднага, без да чака.
* `run()` — тялото на задачата, което се изпълнява **вътре** в нишката. Не се вика
  директно; директното извикване би изпълнило кода в текущата нишка.
* `join()` — блокира главната нишка, докато работната приключи. Резултатът се чете
  от `worker.result` едва след `join()`.

### Защо нишките не пишат в базата

SQLite заключва целия файл при запис. Ако няколко нишки пишат едновременно, се получава
`database is locked`. Затова:

1. Нишките само симулират работа (`time.sleep`) и избират нов статус.
2. Всяка връща обект `ProcessResult` — те не докосват връзката към базата.
3. След `map()` / `join()` главната нишка записва резултатите **последователно**
   чрез `database.apply_results()`.

Изходът от нишките минава през `safe_print()`, който ползва `threading.Lock`, за да не
се смесват редовете на екрана. Всички действия и грешки се записват в
`delivery_tracking.log` с името на нишката.

## 6. Валидация и обработка на грешки

| Случай | Поведение |
|---|---|
| Празен номер за проследяване | Автоматично се генерира следващият свободен `ZIPnnnn` |
| Невалиден формат на номера | `ValidationError` с обяснение |
| Повтарящ се номер | Проверка преди запис + `sqlite3.IntegrityError` като втора защита |
| Празно име или град | `ValidationError` |
| Нулево или отрицателно тегло | `ValidationError` |
| Текст вместо число | `ValidationError` |
| Несъществуваща пратка | Съобщение, действието се прекратява |
| Невалиден избор от менюто | Съобщение, менюто се показва отново |
| Непознато поле за търсене/сортиране | Списък с позволените стойности |
| Грешка при работа с SQLite | `sqlite3.Error` се прихваща, съобщение + запис в лога |
| `Ctrl+C` / `Ctrl+D` | Чист изход без traceback |

Номерата се нормализират (`clean()` + `.upper()`) веднага при въвеждане, така че
`zip1001` и `ZIP1001` се третират като един и същ номер навсякъде.

## 7. Известни ограничения и проблеми

* **Всяка операция отваря нова връзка към базата.** Просто и безопасно за конзолно
  приложение, но при много записи е неефективно — `apply_results()` прави по две
  връзки на пратка (четене + запис).
* **Няма транзакция около групов запис.** Ако записът на резултатите бъде прекъснат по
  средата, част от пратките ще са с нов статус, а друга част — не.
* **Нишките никога не задават краен статус.** По условие се избира случаен статус само
  от списъка „в движение“, така че пратка не може да стане `Доставена` чрез меню 7 —
  приключването е ръчно действие през меню 4. Списъкът с недоставени пратки не се
  изпразва сам.
